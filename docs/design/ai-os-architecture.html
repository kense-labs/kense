AI OS · 架构设计与工程目录结构

一把 API Key 消费全部能力；异构算力、模型、Agent、应用与数据能力统一纳管

完整设计 v2.0 · 全 Rust，无 kstack 依赖 2026-11-08 基线：aster（Rust 内核）× kense 现有 Rust 仓（kpower / kbox / kcl / ksandbox） 命名：职责命名 · 无前缀

定位：AI OS 是「异构资源与 AI 能力的统一供给平面」，不是 AI 应用开发平台。它把 IaaS 算力、MaaS 模型、TaaS 训练、PaaS 应用、AaaS Agent、SaaS 数据能力、开发者供应链收进一个凭证、一套计量、一套审计之下。用户拿一把 Key 调用所有服务，平台负责隔离、路由、计量、审计与回滚。

0x00 : 设计原则

  1. 一把 Key = 一个凭证入口：认证 → 授权 → 计量 → 账单 → 可追责，是平台成立的唯一闭环。
  2. Key 只在边缘出现一次：下游只认短时、降权、限定 audience 的内部身份；沙箱零凭据。
  3. 全 Rust，统一契约与模块边界：控制面与 MaaS 执行面同在 platform 的单 Rust workspace，靠版本化契约与模块边界连接。
  4. 计量点唯一归属资源生产者：网关只记请求数/出网字节，token 归 MaaS，结果条数归 SaaS；嵌套调用挂同一条归属链。
  5. 幂等与补偿先于功能：跨服务写操作默认会失败一半，长 Job 必须状态机 + Saga 补偿，预算与状态同域结算。
  6. 可恢复性靠演练证明：备份、降级、吊销必须定期实测；审计只追加、不可篡改。

边界判定：新增功能前先问「缺了它，一把 Key 的闭环是否断 / 多租户是否不能交付 / 用户是否用不上」；三问皆否则不做。Prompt 注册表、RAG、向量库、独立 LLMOps 产品、内容护栏产品、可视化编排、市场分成、状态页、SLA 赔付、Terraform Provider 等均不做——用户可在 PaaS 自建或接第三方。

0x02 : 总体架构

AI OS 分层　/　九类服务由唯一网关接入，五个横切平面贯穿全栈，底层为异构资源池

供给侧依赖链：IaaS → MaaS → TaaS → PaaS / AaaS → SaaS；下层向上层提供能力，上层向下层回报生产数据。Actions / Packages / Releases 横切供应链，把变更送进这条链；生产轨迹回流为下一轮训练数据。控制面与数据面分离：控制面短暂不可用时，网关按本地策略快照与脏路由表继续服务；吊销是唯一需要全局快速生效的操作，走独立失效广播。

0x03 : 核心领域模型

AI OS 的内核不是某个服务，而是下面七个共享模型。它们决定「一把 Key」是否能成立。

3.1 身份与 Key

Key        = ak_live_{tenant}.{project}.{env}.{random}   // 库内只存 HMAC/argon2id 哈希 + 前缀
Scope      = tenant → project → env                     // 计费 / 配额 / 发布边界
Exchange   = RFC 8693 → SVID / JWT (5~15min, aud 单服务, scope 最小子集, trace_id)
Delegation = on-behalf-of 降权链，禁止原样转发身份（防 confused deputy）

human proof 归 auth，service / workload 归控制面，Key 权威单点；网关 forward-auth 回注 subject / plane / org。不形成两套 Key 体系。

3.2 URN 服务目录

urn:plat:maas:model:*          urn:plat:taas:job:*
urn:plat:aaas:actor:{id}:invoke  urn:plat:saas:tool:get_organization
urn:plat:vault:secret:{name}    urn:plat:releases:channel:prod

注册时声明协议、计量单位、配额维度、SLO、scope 与审计等级；网关据此生成路由、SDK 与文档。所有能力先注册再暴露，避免九套服务各写一遍鉴权。

3.3 计量与账单

Meter = { event_id, trace_id, billing_parent, tenant, project, env,
          key_id, service, resource, quantity, unit, outcome, reservation_id, ts }

各单位经版本化汇率表折算成 credit；长任务创建预扣 → 心跳续扣 → 结束结算；预算判定在网关本地令牌桶，账单链路完全异步。商业账本与 usage ledger 双轨，由架构测试强制不直连。

3.4 审计

Audit = { event_id, seq, prev_hash, hash, actor, auth, delegation_chain,
          action, resource, decision, reason, before, after, diff, result, cost_event_id }

每租户一条只追加哈希链，链头定期外部锚定；敏感动作先落审计再执行；审计员与管理员权限互斥，审计查询本身也产生事件。七类事件：认证凭据、授权决策、资源变更、数据访问、Agent 行为、计费预算、管理动作。

3.5 Vault 凭据模型

Scope      = (organization_id, project_id, environment_id)
SecretRef  = urn:plat:vault:secret:{name}
Credential = { secret_ref, version, ciphertext, key_id, expires_at, aggregate_version }
State      = sealed | active | revoked
Receipt    = { receipt_id, scope, provider, secret_ref, version, status, applied_at }

materialize（封存密文）→ apply（按 scope × provider 激活）→ clear / revoke（终态），每步产生 receipt 并写入审计链；管理面 loopback-only 或经 forward-auth。主 Key 只存哈希，第三方凭据由 Vault 保管，egress 注入只传 secret_ref + version，明文不进沙箱、日志、审计、wire 与 OpenAPI 快照。aster_inf_ 前缀与 /v1/api/__local/vault/* 属线协议值，迁移只改 crate 名不改值。

3.6 发布原语

不可变版本 + 别名 + 流量权重：一套原语同时支撑 PaaS 即时回滚、MaaS canary、TaaS adapter 上下线、Releases 灰度，避免四套语义不一致的实现。评测门禁复用同一套 Benchmark / Judge，服务训练后验证、模型上线与线上回归。

3.7 事件与一致性

Job    = created → reserved → running → succeeded | failed | cancelled → settled
Outbox = PG 单事务写业务状态 + 事件 → NATS，consumer 幂等 apply
补偿   = 发布失败回滚别名 / 任务卡死按租约超时释放预算 / 计量重投按 event_id 去重

九类服务的状态变化统一发事件，供 Actions、审计、通知、计费订阅消费；跨服务不做分布式事务，用 Saga 补偿。事件带签名、重试退避、死信与投递回放。

5.2 命名规则与已占用名

规则内容
无前缀新规划的一切按职责命名：boot / orm / event / flow / vault / core / effect / acp / gateway / control-plane；不带 k、不带组织名、不带产品名。aster-*→k* 的中间方案已废弃
代码中性化业务代码只写职责名：用 boot = { package = "boot", path = "crates/boot" } 这类别名，让 use boot::… 里不出现任何前缀；先例见 kbox/Cargo.toml:116 的 kcl = { package = "kense-kcl" }
品牌适配层product_name / cli_name / domain / tag_prefix / install_dir / bundle_id / credential_prefix / urn_namespace 全部集中在 brand.toml，构建期注入；其余代码零品牌字面量
线协议中性化新增 URN、事件 type、schema 常量一律用中性的 urn:plat:…；历史值（aster_inf_、/v1/api/__local/vault/*、proto 包名）走别名兼容，不硬改
服务 bin用限定名避免同名异物：authd / billing / configd / gateway-runtime / runner / cloud-*；与 CLI 配置库同名的服务叫 configd
历史仓例外kstack / kbox / kcl / kpower / ksandbox / kstudio / kbuddy 是既有 git 仓，保留原名不改（kstack 仅作历史参考，不参与构建与部署）；新代码不新建任何带 k 前缀的目录或 crate，跨仓引用一律用中性别名（box / cl / power / sandbox）
新增vault（凭据模型）、core / effect / acp（Agent 内核）、cloud-contracts / cloud-sdk（契约）——全部无前缀

0x08 : 品牌解耦

结论：能做到「代码与品牌无关」，做不到「系统与品牌无关」。要分三层看，混在一起谈就会既改不干净、又破坏兼容。

层例子能否品牌无关
内部代码标识crate / 模块 / 类型 / 变量 / 目录名、环境变量名、内部别名应该完全无关：用职责命名（boot / orm / event / flow / vault / core），不带任何组织或产品前缀
线协议与持久化URN、API 路径、schema 常量、表名、凭据前缀、事件 type、proto 包名、receipt 格式、OpenAPI operationId首次就应中性；已发布的值是兼容契约，只能别名 + 双读单写 + 版本化迁移，不能直接替换
外部可见标识产品名、CLI 命令、域名、tag 命名空间、安装包名、Bundle ID、证书、用户可见文案、registry namespace必然相关，但应集中在单一品牌适配层；生态渠道（crates.io / npm / Docker / 应用商店）天然要求唯一 namespace，只能用组织中性的名字

最终决定：连组织 namespace 前缀也不进代码。上一版把 k* 定义为「稳定的组织前缀」，本版进一步去掉它——新规划的 crate、目录、服务、契约一律用职责名；k 只保留在既有 git 仓名（kstack / kbox / kcl / kpower / ksandbox / kstudio / kbuddy）里，且这些仓不改名、不新建同前缀目录，跨仓引用通过中性别名隔离。

8.1 三个落地手段

  1. 中性别名：内部依赖用职责名指向带 namespace 的包，业务代码里不出现前缀。 
    [workspace.dependencies]
boot  = { path = "crates/boot"  }
orm   = { path = "crates/orm"   }
vault = { path = "crates/vault" }
    现有先例：kbox/Cargo.toml:116 的 kcl = { package = "kense-kcl", path = "../kcl" } 与 :174 的 ktransport = { package = "kcommon", … }；若发布到公共 registry，namespace 只写在 [package] name，依赖侧用 package = 别名，业务代码仍是 use boot::…。
  2. 品牌适配层：brand.toml 单点定义全部产品可见标识，构建期通过 option_env! / build.rs / Rsbuild define 注入；packaging/ 负责把它写进安装包、tag、图标与文案。config.kcl 里的 .aster/skills、ASTER_* 环境变量、aster-cli-v* tag 都改为读该配置。
  3. 兼容别名期：历史 wire 值不动，新增中性值；读取时新旧都认，写入只用新值，按版本推进。涉及 aster_inf_ 凭据前缀、/v1/api/__local/vault/*、.aster.grok.tools.v1.* proto 包名、ASTER_PAIR_BUILD_ID、openapi/v1.json 的 operationId 与 tag。

8.2 判定标准与代价

一句话验收：把公司 / 产品名换掉，需要改几个文件？答案应该是 1 个 brand.toml + 打包脚本，而不是全仓两万处替换（对照 Octop→kbuddy 曾做过 19,574 处替换）。CI 增加门禁：品牌字面量只许出现在 brand.toml 与 packaging/。

必须接受的三个代价：① 已发布 wire 值不能凭空消失，别名期会同时存在新旧两套字符串；② 生态渠道必须有一个组织 namespace，只能做到「中性 + 与产品品牌分离」；③ 改名应用器是一次性迁移工具，不是长期依赖，最终状态是改配置即可发布新品牌。

对落地路线的影响：P0 的「改名应用器」目标从「全量 aster→k」改为「清掉产品品牌词 + 建立 brand.toml + 加品牌字面量门禁」；P3 的 wire 白名单升级为「别名双读单写」；P5 拆分发布通道时，tag 前缀与 latest.json 由 brand.toml 生成。aster 这个仓库名本身可以保留（它是上游仓库的历史名），但仓库内的代码与产物不再依赖它作为品牌。
