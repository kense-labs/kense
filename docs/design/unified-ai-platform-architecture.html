核心主张：不要把它做成八个并列的产品，每个产品各自接一遍鉴权和计费。正确形态是「一条自下而上的供给侧依赖链 + 一个统一网关 + 四个横切平面（身份与策略、计量与计费、可观测与服务目录、审计与合规）」。一把 Key 打通的是身份、配额、预算、审计和账单，而不只是「能调通接口」。

0x00 : 设计原则

  1. Key 只在边缘出现一次。密钥绝不下发到业务服务或沙箱；下游只认短时、降权、限定 audience 的内部身份。
  2. 计量点唯一归属资源生产者。网关不重复统计 token，模型服务不重复统计请求数；嵌套调用挂同一条归属链。
  3. 所有能力先注册再暴露。服务目录以 URN 声明 scope、计量单位、配额维度与 SLO，网关由此生成路由和策略。
  4. 控制面与数据面分离。控制面短暂不可用时，已建立的数据面请求必须继续可用（本地策略快照 + 脏路由表回退）。
  5. 同步与异步分开建模。推理请求走请求/响应；训练、构建、批量、长驻 Actor 一律走 Job + 事件 + 预算预扣/结算。
  6. 审计是一等平面。审计 ≠ 日志 ≠ Trace ≠ 计费；必须只追加、不可篡改、与管理权限隔离，并在 P0 就上线。
  7. 幂等与补偿先于功能。跨服务写操作默认会失败一半，长 Job 必须显式状态机 + Saga 补偿，预算与状态同域结算。
  8. 配额不等于容量。限流与预算只管「允许用多少」，物理资源争抢必须有独立的优先级、抢占与公平调度。
  9. 可恢复性靠演练证明。备份、降级、吊销必须定期实测，未演练过的能力不算具备。
  10. 能复用就不自建。MaaS 直接以现有 kstack 为底座；网关、沙箱、制品、工作流优先采用成熟开源实现。

0x04 : 统一身份与「一把 Key」

设计判断：「一把 Key」应理解为「一个凭证入口」，不是字面意义的全局万能长期密钥。默认一把主 Key 即可使用全部服务，但架构必须支持派生受限子 Key、即时吊销、双活轮换、每 Key 预算硬顶；否则一次泄露等于全平台加全部预算失守。

4.1 Key 模型

ak_live_<tenant>.<project>.<env>.<base62-random>
存储：prefix 索引 + HMAC-SHA256 / argon2id 哈希（明文仅创建时展示一次）
绑定：tenant_id · project_id · env · policy_set · budget_id · quota · expires_at
能力：scope 白名单（URN 前缀）、速率上限、并发上限、预算硬顶、IP/来源限制、可吊销、可轮换

4.2 统一服务目录（URN）

任何服务上线前注册：URN 前缀、协议、计量单位、配额维度、SLO、所需 scope、审计等级。网关据此生成路由、策略与文档，避免九套各自实现鉴权。

urn:plat:gw:route:*                     统一网关路由
urn:plat:maas:model:*                   OpenAI /v1 模型
urn:plat:maas:deployment:{id}:*        部署与副本管理
urn:plat:taas:job:*                     训练任务
urn:plat:taas:dataset:{id}:*            数据集与版本
urn:plat:paas:project:{id}:deploy      应用发布
urn:plat:aaas:actor:{id}:invoke        Agent 调用
urn:plat:saas:tool:get_organization    资源层工具（按结果计费）
urn:plat:actions:workflow:*             CI/CD
urn:plat:packages:artifact:*            制品
urn:plat:releases:channel:prod          生产发布通道
urn:plat:iaas:vm:*                      云主机

4.3 信任传播（RFC 8693 Token Exchange）

  1. 客户端持主 Key 调用网关；网关用本地策略快照校验哈希、scope、预算、限流，生成 trace_id 与 budget_reservation_id。
  2. 网关换取 5–15 分钟的 SPIFFE SVID / JWT：aud 限定单个服务，scope 取本次所需最小子集，携带 tenant/project/trace/reservation。
  3. 下游服务不认主 Key，只验证内部身份；AaaS 沙箱内无任何平台凭据。
  4. 服务间调用使用 on-behalf-of 并继续降权，禁止原样转发身份（防 confused deputy），每跳写 delegation chain，并落为审计事件与授权链证据。
  5. AaaS 需要访问外部 SaaS 时，由 egress 网关按策略从密钥库取凭据并注入 outbound 请求，沙箱自身零凭据、默认无出网。

0x05 : 计量与计费闭环

5.1 统一 meter 事件

{
  "event_id": "01J...",                 // 幂等键，ULID
  "trace_id": "4bf9...", "span_id": "a1c2...",
  "billing_parent": "01J...",           // 嵌套调用指向父计量事件
  "tenant": "acme", "project": "chatbot", "env": "prod", "key_id": "ak_...7f",
  "service": "maas", "resource": "model/qwen3-8b",
  "quantity": 1832, "unit": "token", "dimension": "output",
  "outcome": "ok | no_result | failed | cached",
  "reservation_id": "rsv_...", "ts": "2026-11-08T04:00:00Z"
}
  • 归一化：各层单位经带版本的汇率表折算成 credit，按 tenant / project / env / service / trace 聚合出账单与成本树。
  • 防重复计费：计量点唯一归属资源生产者。网关只记请求数与出网字节；token 由 MaaS 记；GPU·秒由调度器记；结果条数由 SaaS 记；actor·秒由 AaaS 记。
  • 嵌套归属：AaaS → MaaS → SaaS 是三次真实成本，各记各的，用 billing_parent 串到同一 trace_id，账单可展开、可审计、可证明无重复。
  • 按结果计费：SaaS 仅 outcome=ok 且非空结果 计费；缓存命中、校验失败、空响应不收费；字段带 source/method/as_of。
  • 预扣与结算：短请求在网关按上限预扣；长 Job 创建时按估算预扣 → 心跳续扣 → 结束按实际结算、多退少补；预算耗尽按策略拒新请求或优雅终止运行中任务。
  • 可用性隔离：预算判定在网关本地（令牌桶 + 周期对账），账单链路异步（事件流 → 流处理 → 账库），挂账不阻塞请求路径；event_id 去重保证幂等。
  • 与审计解耦：meter 事件用于计费、可归档；审计事件只追加、不可改，两者用 trace_id / cost_event_id 关联，但存储与留存策略独立（见第 06 节）。

0x06 : 审计与合规平面

先分清四件事：日志记录「系统发生了什么」，Trace 记录「一次请求怎么走」，meter 记录「该收多少钱」，而审计记录「哪个主体、在何时、用什么凭据、对哪个资源做了什么动作、结果如何，且能证明这条记录未被篡改」。v0.1 只做了前三者加零散的审计提及，这是本版补齐的缺口：一把 Key 覆盖全平台，没有独立的不可抵赖层，出事时回答不了「谁把生产环境的模型版本换了 / 谁导出了数据集 / 谁提升了子 Key 的 scope」。

6.3 不可抵赖与生命周期

  • 只追加 + 哈希链：每租户一条链，事件含 prev_hash 与 seq；定期把链头锚定到外部只写存储或透明日志，使内部管理员也无法无痕删改。
  • 权限分离：审计员角色与平台管理员分离；管理员不能删改审计记录；每一次审计查询本身也产生审计事件。
  • 写入语义：普通动作异步入事件流；敏感动作（发布到 prod、Key 吊销、角色变更、数据集导出）必须先落审计再执行，审计系统不可用时拒绝该动作而非静默放行。
  • 关联与隔离：用 trace_id 展开技术链路、cost_event_id 对上账单，但审计库与账单库、日志库独立——账单可归档清理，审计不可改。
  • 留存与取证：默认 1 年热存 + 冷归档（可按合规要求配置）；提供按 actor / resource / action / decision / 时间检索、SIEM 导出、合规包（带哈希链校验结果）与法律保全 hold。

6.4 与现有底座的差距及落地节奏

kstack 已有可复用的碎片：credential-safe 命令日志（internal/commandlog 的 Redact）、限时调试会话（internal/debuglog）、终端会话审计记录（store.TerminalSessions，含 CloseReason）、请求时间线（uxrecord）、稳定错误码契约。但它们分散在不同库表、无统一 schema、无哈希链、无审计员隔离，属于「可观测」而非「审计」。

  • P0 必做：认证与凭据、授权 deny、资源变更、管理动作四类 + 统一审计事件 schema。审计不能推到后期补，否则历史窗口永远空白。
  • P1：Agent 行为、计费与预算、哈希链与外部锚定、审计员角色。
  • P2：数据访问分级、合规包导出、法律保全 hold。

0x08 : 控制面 / 数据面与可用性

  • 本地策略快照：网关缓存 Key 哈希、scope、配额、路由表与服务目录版本；控制面不可用时按最后一份快照继续服务（可直接复用 kstack 的路由表 2s 刷新 + 脏快照回退机制）。
  • 吊销传播：Key 吊销是唯一需要「快速全局生效」的操作，走独立的高优先级失效广播（而非等待快照 TTL）。
  • SLO 分级：网关与 MaaS 数据面 P99 目标最严；账单、分析、报表允许分钟级延迟；TaaS / Actions 为异步任务，用事件与状态机而非超时重试。
  • 多区域：IaaS 资源池按区域自治，控制面全局唯一（或主备），计量事件就近写入后汇聚；跨区调用在网关层按 URN 前缀路由。
  • 隔离粒度不一致是现实：IaaS 是 VPC、MaaS 是部署/副本、PaaS 是函数、AaaS 是单 actor 沙箱。不要假装有一层统一隔离，而要在服务目录里显式声明每层的隔离等级与合规边界。

0x0C : 风险与待定决策

权限半径单 Key 覆盖全平台，一旦泄露影响面最大。缓解：子 Key、预算硬顶、scope 白名单、即时吊销、异常行为检测。
重复计费嵌套调用与网关/服务双统计是高频事故。缓解：计量点归属规则 + billing_parent + 事件幂等。
长任务预算训练与挂起 actor 可能跑数天。缓解：预扣 + 心跳续扣 + 到期策略（终止 / 降级 / 通知）。
控制面单点所有服务依赖统一 IAM，挂了全平台停摆。缓解：本地策略快照、吊销走独立广播、账单链路完全异步。
隔离粒度不齐VPC / 副本 / 函数 / actor 沙箱各不相同。缓解：服务目录显式声明隔离等级，合规按最弱环评估。
审计不可抵赖管理员能删日志就等于没有审计。缓解：哈希链 + 外部锚定、审计员权限分离、审计查询自身留痕、敏感动作先落审计再执行。
多租户改造单租户 SQLite 上叠 IAM 是假隔离。缓解：先垫片再迁 PG + RLS，强制查询门禁，按租户分批切流并可回退。
跨服务不一致发布成功但部署失败、扣费成功但任务卡死。缓解：幂等键 + Saga 补偿 + Job 状态机 + 日终对账。
吵闹邻居单租户训练占满 GPU 使他人推理饿死。缓解：资源池分级、优先级抢占、加权公平队列、超卖保护线。
密钥泄露一把 Key 权限半径大。缓解：短时子 Key、双活轮换、吊销广播、泄露 runbook 与审计回溯。
数据合规SaaS 跨源聚合与训练回流涉及授权与来源。缓解：source/method/as_of 全链路标注、只采授权源、字段只增不改。

需要你拍板的五件事

  1. 部署形态：单区域单集群起步，还是一开始就要多区域自治？这决定控制面是否必须做成主备 + 分区计量。
  2. IaaS 边界：自建 ZStack 私有云做完整 IaaS，还是只做「对接已有云 + 资源池抽象」？后者能省掉一大块。
  3. 计费模型：纯预付费 credit，还是后付费 + 预算闸？影响预扣/结算的复杂度与风控强度。
  4. 生态策略：SaaS 资源层与 Packages 是否允许第三方注册与分成？决定服务目录是否需要开放审核与计量对账。
  5. 多租户改造力度：接受「网关垫片 + 映射」的内测方案先上线，还是一开始就做 kstack 数据层的 PostgreSQL / RLS 改造？这是 P0 工作量与隔离真实性的取舍，其余四项决策都受它影响。

0x0D : 多租户与资源治理

这是本轮审计发现的最致命缺口：v0.2 假设了 tenant / project / env 存在，却没设计它们如何落地。「一把 Key」若只是给单租户系统加一层认证，等于把全部租户数据放进同一个库、同一个调度队列，权限再细也没用。

13.1 隔离模型与数据层演进

  • 三层边界：tenant（计费与合规主体）→ project（资源与配额边界）→ env（dev / staging / prod，发布与预算边界）。所有表、所有查询、所有缓存键、所有计量事件都必须带齐三者。
  • 隔离分级：共享表 + 行级策略（默认）／独立 schema（付费大客）／独立库或独立集群（合规客户）。分级写在服务目录里，不靠人工约定。
  • 强制门禁：把「每个持久化查询必须带 tenant 上下文」做成静态检查，像 kstack 现有的 i18n-check / check-architecture 一样进 CI；ORM 层统一注入 tenant 过滤，禁止裸查询绕过。
  • 现实差距：kstack 当前是单管理员 + 单 SQLite 文件（kstack.db 等 5 个库），无 tenant_id。必须先迁到 PostgreSQL + RLS（GORM 换 dialect、写迁移与回填脚本），否则多租户无从谈起。详见 17.2。

13.2 组织与权限模型

角色典型权限约束
平台管理员全局配置、服务目录、配额模板不能读审计原始库、不能改审计记录
组织所有者成员、预算、子 Key、环境受组织预算上限约束
开发者部署、训练、构建、调用按 env 授权，prod 需审批
审计员只读审计检索、合规包导出与平台管理员权限互斥
财务 / 账单只读账单、成本、发票不可改预算、不可调账

补 SSO / SCIM 做成员生命周期，人类账号与服务账号分离；高危操作走 JIT 临时提权（申请 → 审批 → 限时 → 自动回收 → 全链路审计），杜绝常驻超级管理员。所有提权与角色变更都是 06 章的管理动作审计事件。

13.3 配额不等于容量仲裁

v0.2 只写了 quota 与 budget，缺的是「物理资源不够时谁先用」。quota 限并发/速率上限、budget 限金额上限，任一触顶拒绝新请求；但两者都不解决吵闹邻居。必须补：

  • 资源池分级：预留（承诺折扣、保障）／按需（加权公平）／抢占式（Spot，可被回收），并明确超额订阅比例与超卖保护线。
  • 优先级与抢占：在线推理 SLO > 交互式训练 > 批量训练 / 批量推理 > CI 构建；低优先级被抢占时按 checkpoint 恢复并退还预扣预算。
  • 公平调度：按 tenant/project 加权公平队列或 DRF（主导资源公平），GPU 显存、卡时、RDMA 带宽、存储 IO 多维度同时计量，避免单租户占满 GPU 导致他人推理饿死。
  • 容量闭环：用 meter 事件反推容量与成本归因（内部成本 vs 售价、毛利），指导扩容与售卖上限。

0x0E : 可靠性、一致性与容灾

14.1 幂等、状态机与跨服务补偿

九类服务里大量操作跨越控制面与执行面，v0.2 没有定义「做了一半失败怎么办」——这会直接造成账单与状态不一致。补三条硬规则：

  • 所有写操作携带 Idempotency-Key（24h 去重窗口），长 Job 走显式状态机：created → reserved → running → succeeded | failed | cancelled → settled，settled 之前预算不得释放。
  • 跨服务用 Saga + 补偿，不做分布式事务。三个必须预先写好补偿的场景：
    ① Releases 已 promote 但 MaaS 部署失败 → 自动回滚 release 指针、退还预留、发事件；
    ② 训练 Job 卡死但预算持续预扣 → 租约 + 心跳 + 超时补偿，孤儿任务定时清理；
    ③ 计量事件重复投递 / 账单已出 → event_id 幂等 + 日终对账补差，绝不重扣。
  • Job 状态与预算结算必须同事务域（或显式对账），「任务成功但没结算」与「扣了钱但任务没跑」都算 P0 事故。

14.2 降级矩阵

故障行为禁止
控制面不可用数据面按本地策略快照与脏路由表继续服务禁止重新鉴权依赖远程调用
审计不可用普通动作异步排队重试；敏感动作直接拒绝禁止静默放行
计费 / 计量不可用本地令牌桶继续预算判定，事件落本地盘后补投禁止丢计量事件
网关单实例故障无损重启 + 连接排空，路由表从快照恢复禁止有状态会话绑死实例
单区域不可用按 URN 前缀重路由到健康区，降级为只读或排队禁止跨区搬运受限数据
GPU 池耗尽按 13.3 优先级排队 / 抢占 / 拒绝并给出原因码禁止无限等待不释放预算

14.3 备份、RPO / RTO 与演练

  • 分级目标：控制面元数据 RPO≈0 / RTO < 15min；账单与计量 RPO < 1min；审计 RPO = 0 且不可丢；日志与 Trace 允许有损。
  • 备份：加密 + 异地 + 版本化，覆盖控制面数据库、服务目录、策略、制品清单与 KMS 密钥托管材料；没有定期恢复演练的备份不算备份，演练结果进审计报告。
  • 审计链是最后防线：06 章的哈希链头外部锚定，即使控制面被完全摧毁也能验证历史未被篡改。
  • 爆炸半径：按 tenant / region / 服务切故障域，灰度与特性开关可按租户比例放量；禁止单一主 Key 或单控制面把全平台带走。

0x0F : 安全与合规补完

15.1 密钥生命周期与泄露响应

v0.2 有轮换与吊销的能力，没有流程。补：主 Key 90 天提醒轮换、子 Key 30 天、SVID 分钟级、双活轮换窗口；平台自身密钥走 KMS 信封加密与静态加密；制品与日志做 Secret 扫描。泄露响应 runbook：检测 → 立即吊销 → 轮换受影响凭据 → 用 06 章审计链回溯首次使用时间与影响面清单 → 冻结相关预算 → 通知与复盘，全程可导出为证据包。

15.2 东西向零信任与边缘防护

v0.2 只覆盖了南北向网关与 AaaS egress。补：服务间一律 mTLS（SVID）+ 网络策略默认拒绝；管理面与数据面网络分离；TLS 证书自动轮换；WAF / DDoS / 速率异常检测放在统一网关之前；跨区域与跨云走私有连接而非公网；语义缓存与前缀亲和路由必须按 tenant 分区，防跨租户缓存污染与信息泄露。

15.3 数据生命周期、驻留与血缘

  • 数据分级：公开 / 内部 / 机密 / 受限，决定加密、留存、导出与审批要求。
  • 驻留：tenant 绑定 region，数据与派生模型不得跨区；训练产物继承数据集的驻留标签（14 章跨区降级时据此拒绝）。
  • 删除权：删除必须传播到备份、冷归档、缓存、制品副本与下游模型；审计记录按合法例外保留但需去标识化。
  • 血缘：数据集 → 训练 Job → adapter → Release → 推理部署 → 请求轨迹 → 下一轮样本 全程可追溯，是模型复现、合规举证和「哪个版本用了被删除数据」的唯一依据。

15.4 AI 特有威胁

17.2 从 kstack 单租户演进到多租户的迁移路径

这是把蓝图落到现有代码的关键一步，也是最容易被低估的风险。分三步走，每步可独立回滚：

  3. 职责拆分：IAM / 计费 / 审计 / 服务目录独立成平台控制面，kstack 收敛为 MaaS 资源执行面，通过短时 SVID 接收指令；旧管理 API 保留兼容层并在弃用期后下线。全程双写 + 对账 + 按租户分批切流，任一批次异常可回退到垫片期映射。

0x12 : 必要功能边界（收敛版）

为什么要收敛：v0.5 按竞品全集做功能对照，把 Bedrock / Dify / Vercel / GitHub 的能力都算成「缺口」，清单膨胀且偏离定位。本平台的定位是「异构资源与 AI 能力的统一供给平面」，不是「AI 应用开发平台」；竞品有，不等于我们必须有。本章按三条标准重新裁剪：满足其一才算必要。

13.3 契约层才是架构核心

  1. 一份 contracts 包：版本化 DTO + URN 服务目录 + HTTP 路径常量 + *_SCHEMA_V1；OpenAPI 由路由表生成并做快照测试防漂移（aster openapi/v1.json 范式），错误信封沿用 kstack 的「稳定 CODE + params + 英文 fallback → UI 本地化」并由 i18n-check 强制一一对应（今早已修复该契约的一处违规）。Rust / Go / TS 客户端全部由契约生成。
  2. 统一 Harness Adapter 作防腐层：aster docs/architecture/harness-gateway.md 把 ACP / HTTP-gRPC / SDK / CLI / A2A 映射为「发现能力、准备、提交、观察、交互、取消恢复、收集结果」7 个操作，TaskSpec / RunBinding / HandoffBundle / TaskResult 不携带协议专属字段。用它收编 kstack 的 agent WS 协议、aster ACP、MCP 与 A2A；该文档自述「尚未编码和联调」，正是可落地的空白位。
  3. 身份边界复用 identity-split：human proof 归 auth、service/workload 归控制面、Key 权威单点，gateway forward-auth 回注 subject/plane/org。对应「一把 Key → 短时 SVID → 网关 PEP」，不要形成两套 Key 体系。
  4. 计费双轨不变量：aster billing 明确「member-plane 商业账本」与「Cloud durable usage ledger」双轨并由架构测试强制（billing_stays_off_cloud_stores）。对应 meter→credit 与账单分离，建议直接采用该不变量并写成架构测试，防止跨库直连。
  5. 不可变身份三元组：(unit_id, generation, canonical_spec_digest) + request_id 与 digest-bound receipts，解决派单丢 ACK、delivery_unknown 与幂等 apply——补上 0x0E 的补偿场景实现细节。

  • 不照搬 aster：ACL 单一配置语言（与 Go 生态冲突）、Tauri/Studio 桌面门禁、四套 Cargo.lock 与 edition 混用（迁移期妥协）、spec-kit 多阶段全流程、apps/api 扩展面（IM/日程/邮箱）、use-registry 桌面插件 TUF 树。
  • 必须收敛 aster 的历史包袱：api / cloud / control-plane 三处重复的 auth / billing / config 源码副本合并为单一权威；billing 在控制面侧另建 usage ledger，不复用 member-plane 商业账本。
  • kstack 侧硬约束：单管理员 + 单 SQLite + 无 tenant_id + GORM dialect 绑定 + UI 与 server 同仓 embed —— 控制面必须独立，kstack 退化为执行面；按 0x11 三步迁移（垫片映射 → PG+RLS 双写回填 → 职责拆分），双写对账、按租户分批切流、可回退。
  • 前提风险：kstack 源码不在本机，且 aster 的 sandbox / box / oci-runtime 仅存 .tmp 快照、harness-gateway 未编码 —— 这三项在落地前需重新检出与补齐，不宜当作现成可用组件排期。

13.6 与 0x12 的对应及落地顺序

本章不新增功能，只给 0x12 的 12 项必要功能选实现载体：凭证 / 目录 / 权限 → control-plane + contracts + gateway forward-auth；计量 / 审计 / 一致性 / 事件 → PG Outbox + 计费双轨 + meter 契约；发布闭环 → contracts 版本 + kstack 已有签名发布通道；控制台与 API → React/Rsbuild + OpenAPI 生成 SDK；各层最小能力 → maas（kstack）+ agent-runtime（aster Core）。

落地顺序：① 先立 contracts 与 Regime 规约，冻结 URN、错误码与 OpenAPI 快照；② gateway 与 control-plane 组成最小「一把 Key」闭环（复用 aster 已实现部分）；③ kstack 以垫片方式接入，验证计量与审计链路；④ agent-runtime 经 Harness Adapter 接入；⑤ 最后做 kstack 数据层 PG+RLS 迁移与职责拆分。

0x14 : Vault 凭据模型

14.2 统一抽象与状态机

Scope      = (organization_id, project_id, environment_id)
SecretRef  = urn:plat:vault:secret:{name}
Credential = { secret_ref, version, ciphertext, key_id, expires_at, aggregate_version }
State      = sealed | active | revoked
Receipt    = { receipt_id, scope, provider, secret_ref, version, status, applied_at }

三阶段 materialize（封存密文）→ apply（按 scope × provider 激活为 active binding）→ clear / revoke（终态），每步产生 receipt 并写入 0x06 的审计链。管理面 loopback-only 或经 forward-auth，不暴露公网。

14.3 与一把 Key 的关系及不变量

  • 职责分离：主 Key 只存哈希（0x04）；第三方上游凭据由 Vault 保管；Token Exchange 发的是短时身份，不是凭据本身。
  • 零明文外泄：egress 注入只传 secret_ref + version，明文不进沙箱、日志、审计事件、wire 与 OpenAPI 快照（呼应 0x06 字段约束）。
  • 轮换与撤销：轮换必须递增 version 并留 receipt；撤销是终态，aggregate_version 与 state 受数据库约束强校验。
  • 线协议不改名：aster_inf_ 前缀、secret_ref 格式、/v1/api/__local/vault/* 路径属于 wire 值，迁移时只改 crate 名不改值（呼应 0x13 R2）。
