Kense OS · 架构审查

审查对象：kense-os-modules.html 的 16 张模块图与模块职责，对照 ai-os-architecture.html v2.0 与 unified-ai-platform-architecture.html v0.8
2026-11-08错误 / 可达性 / DDD 三个维度结论：图可作为模块速查，不可作为架构依据

总结论　16 张图在视觉风格、模板与命名上是一致的，作为「每个模块做什么」的速查表合格；但作为架构表达不成立：模块之间的边几乎全部丢失，17 条声明引用中 16 条只有一端；0x01 的 12 项必要功能有 3 项完全没有对应模块，0x03 的七个领域模型缺了 2 个；按 IaaS/MaaS/… 的部署形态切分不是 DDD 的限界上下文，七个共享模型构成一个没有 owner、没有防腐层的隐式大内核。

0x01 : 错误清单

#类型问题与证据处置
A1事实错误MaaS 约束条只列 6 个 crate，漏了 node-agent；而同一模块中文说明写的是 7 个，0x04 表格与正文均明确 7 个。图内自相矛盾。已修复并重渲染全部 SVG/PNG/HTML；约束条现为 RUST 7 CRATES: … node-agent …，目视确认无溢出。
A2语义串位Identity 的 IN 写的是 Key 的字符串格式（ak_live_{tenant}…），是数据结构不是输入事件；OUT 写 subject / plane / org re-injected at gateway，这是网关 forward-auth 的回注动作，不是 Identity 的产出。Identity 真正的产出应是 5–15 分钟的 SVID / JWT。重画该模块：IN = 认证请求 / Key 出示，OUT = 短时降权令牌。
A3模板误用「输入 → 核心 → 输出」是数据流模板，被强加给共享内核型模块后普遍不成立：Metering 的 IN 是转换过程、Audit 的 OUT 是查询能力、IaaS/SaaS 的 OUT 是对外抽象（0x03 表头即「对外抽象」）、Pool 的 IN 是硬件构成。控制面五模块改用「契约 / 不变量 / 被谁调用」模板，不画流水线。
A4语义不统一底部橙条混装四种语义：架构约束（Gateway/Vault/Audit）、实现清单（MaaS）、计量单位（AaaS）、设计口号（URN/Releases）。统一为「该模块不可让渡的一条不变量」，实现细节移入中文说明。
A5源文档冲突unified-ai-platform-architecture.html:229 写「八类服务」，ai-os-architecture.html:100 与图集写「九类服务」。图集沿用 v2.0 口径，但两份蓝图未对齐。以 v2.0 九类为准，回改早期蓝图口径或标注版本差异。

0x02 : 可达性 / 不可达

机器核对　从每个模块的 OUT/STRIP 与 IN/ROLE 中提取对其它模块名的引用：8/16 个模块有出边、3/16 个有入边；共 17 条声明引用，其中 16 条只有一端声明。16 张图彼此独立，HTML 里没有放 0x02 总体架构图，因此从图集本身无法重建任何一条完整调用链。

两处设计语义问题（源文档层面）

  • 供给链 ≠ 调用链：IaaS → MaaS → TaaS → PaaS / AaaS → SaaS 是能力供给方向，但 PaaS 的 Git build 不依赖 TaaS，AaaS 的 actor 也不依赖 TaaS。按调用依赖读这条链不成立；应区分两种箭头语义。
  • 降级路径未表达：0x08 的「本地策略快照续服务」与「吊销独立广播」是控制面不可用时数据面仍可达的唯一机制，图集未画；Gateway 橙条只写了主 Key 不转发。

0x03 : DDD 领域驱动设计评估

已经做对的　七个共享模型是领域模型而非 CRUD 表；Job 状态机、Outbox + 幂等 + Saga 补偿、审计 append-only + 外部锚定、Vault 的 sealed/active/revoked + receipt，都有明确的不变量与生命周期；「计量点唯一归属资源生产者」体现了不变量归属聚合的意识；不可变版本 + 别名 + 流量权重可作为 Published Language；独立 contracts/ 仓 + 生成客户端接近 Open Host Service。

DDD 要素判定依据与影响
限界上下文不符合IaaS / MaaS / TaaS / PaaS / AaaS / SaaS 是部署形态与商业模式，不是通用语言边界。同一概念（Deployment / Replica / Instance / Job / Actor / Session）跨上下文漂移。
上下文映射 Context Map缺失九服务 × 五横切平面之间没有任何关系模式（Customer-Supplier / Conformist / ACL / Shared Kernel / OHS）定义。这正是可达性问题的根因——不是图少画了箭头，是边界契约没定义。
共享内核过大Key、URN、Meter、Audit、Vault、发布原语、事件一致性七个模型被九个服务共用，构成没有 owner、没有变更审批、没有防腐层的隐式大内核。
聚合根 / 不变量边界未标注0x03 给了数据结构但没给聚合边界。0x00 原则 5 要求「预算与状态同域结算」，而 Metering 与 TaaS 是两张图、两个上下文，一致性边界无处落地。
领域事件偏技术3.7 是「状态变化统一发事件」，缺事件风暴产出的业务事件名（ModelDeployed / AdapterEvaluated / BudgetExceeded / CredentialRevoked），也没区分内部领域事件与跨上下文集成事件。
分层 / 六边形未分离Rust crate（catalog / gpu / scheduler / state / inference）按技术职责命名，是数据 + 算法，没有 domain / application / infrastructure 分层与端口，领域逻辑易被基础设施渗透。
通用语言不统一同一 unit 在不同层含义不同；只有 URN 是显式 Published Language，其余概念无 glossary。

建议的整改顺序

  1. 先补一张总体依赖图放进图集（直接复用 0x02 总览图），并给每张模块图加「上游 / 下游」脚注，让 17 条边两端闭合。
  2. 补齐三个缺失模块：Event & Consistency（Outbox/Saga/幂等/补偿）、Event Notification（SSE/Webhook）、User Entry（Console/REST/SDK/Docs），并把「发布原语」提为独立横切模块。
  3. 重划限界上下文：把 16 个「层」映射为约 9 个上下文——Identity & Access、Service Catalog、Metering & Billing、Audit & Compliance、Secret Management、Model Supply（IaaS+MaaS+资源池）、Training & Evaluation、Delivery & Supply Chain（PaaS+Actions+Packages+Releases）、Agent Runtime（AaaS+SaaS）。
  4. 画 Context Map 并标关系模式，为共享内核加 ACL；把 contracts/ 定为 Published Language 的唯一 owner，URN 加版本与变更审批；每个上下文标聚合根、不变量与领域事件；Rust crate 按 domain / application / infra 分层。
