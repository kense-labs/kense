基于 2026-11-09 对 platform/、apps/、crates/ 与组织仓库的只读实证；不改线协议、不改历史仓名
31 个 crate 目录 · 27 个顶层 manifest42 项本地依赖别名 3519 个 .rs 含 aster_ 引用15 个组织公开仓

一句话结论　架构目前按部署形态与技术层切分（apps/ + crates/、IaaS/MaaS/…），不是 DDD 的限界上下文；命名则是三层脱节：目录用职责名（boot）、[package] 用品牌名（aster-boot）、代码里又写回品牌（use aster_boot）。中性别名层其实已经建好，但和 aster-* 别名双轨并存，等于两套官方写法。优化要按「内部标识 / 线协议 / 外部可见」三层分开做，不能一刀切全局替换。

0x01 : 架构设计分析

1.1 当前切分方式的问题

  • 按交付形态而非业务能力切分：IaaS / MaaS / TaaS / PaaS / AaaS / SaaS 是「卖什么」，不是通用语言的边界。同一个概念（Deployment / Replica / Instance / Job / Actor / Session）在多个层里漂移。
  • apps/ 与 crates/ 是物理分层，不是领域分层：apps/config 只是指向 control-plane/config 的符号链接，apps/runtime 的包名却是 aster-gateway-runtime；目录、包、二进制三者各说各话。
  • 共享内核过大且无 owner：Key / URN / Meter / Audit / Vault / 发布原语 / 事件一致性 七个模型被九个服务共用，没有 Context Map 与防腐层——这也是上一轮审查里「16/17 条边单端」的根因。
  • 供给链与调用链混用：IaaS → MaaS → TaaS → PaaS/AaaS → SaaS 是能力供给方向，但 PaaS 的 Git build 不依赖 TaaS；两种箭头语义应分开画。

4.4 架构模块名

Gateway / Identity / URN Registry / Metering / Audit / Vault / Actions / Packages / Releases / Heterogeneous Resource Pool 本来就是职责名，全部保留。IaaS/MaaS/TaaS/PaaS/AaaS/SaaS 是行业通用分层术语，也保留，但要在图与文档里明确「供给侧能力链 ≠ 运行时调用链」，并在 0x01 的 9 个限界上下文里给出业务语义的正式名称。

0x06 : 验收标准

  1. 把产品 / 组织名换掉，需要改几个文件？答案应是 1 个 brand.toml + 打包脚本。
  2. rg "aster_|aster-|kense-" --glob "*.rs" --glob "Cargo.toml" 在 brand.toml / packaging/ / 白名单 wire 值之外应为 0 命中。
  3. 目录名、别名、package 名、use 名四者一致；每个缩写（sag / okf / apofasi）在术语表有定义。
  4. 每个限界上下文有 owner、聚合根与不变量声明；Context Map 标出全部关系模式。
本方案为只读分析 + 命名建议，未改动任何仓库代码或配置。实证数据来自 platform/Cargo.toml、migrated/crates/*/Cargo.toml、apps/*/Cargo.toml、gh repo list kense-labs 与 ai-os-architecture.html 5.2 / 0x08。线协议与历史仓例外以设计文档为准。
